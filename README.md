# ReqGuard: ИИ-агент проверки требований

Агент проводит **статическое ревью документа требований до разработки** по
ISO/IEC/IEEE 29148:2018 (п. 5.2.5 и 5.2.6) и IEEE Std 830-1998 (п. 4.3).
Он нарезает документ на требования, проверяет каждое требование и весь набор,
формулирует уточняющие вопросы автору и записывает отчёт на русском языке.

Кейс: BCC-HUB x MNU Agent Challenge 2026, задача «Агент проверки требований».

## Быстрый старт

```bash
git clone https://github.com/ErsultanN/req-agent && cd req-agent
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                                     # впишите GEMINI_API_KEY
python -m validator samples/requirements.md reports/report.md
```

PDF и DOCX читаются так же: `python -m validator путь/к/документу.pdf reports/report.md`.

Отчёт ляжет в `reports/report.md`, а рядом в `reports/report.json` будут те же данные в машиночитаемом виде.

### Как получить ключ LLM

1. Откройте <https://aistudio.google.com/apikey> и войдите в Google-аккаунт.
2. Нажмите **Create API key** (бесплатный тариф, карта не нужна).
3. Вставьте ключ в файл `.env` в корне проекта: `GEMINI_API_KEY=...`.

Модель по умолчанию `gemini-3.6-flash`. Ключи AI Studio сейчас имеют формат `AQ.…`: это нормально.
Модель можно сменить в `.env` (`GEMINI_MODEL`) или флагом `--model`. Агент также работает с
OpenAI-совместимыми API, Anthropic и локальной Ollama: см. `.env.example`.

## Команда запуска

```text
python -m validator <файл требований> <файл отчёта> [опции]

  -i, --interactive   после анализа задать уточняющие вопросы в терминале и учесть ответы
  --answers FILE      учесть ответы из JSON {"Q1": "…"} (воспроизводимый прогон)
  --provider P        gemini | openai | anthropic | ollama
  --model M           имя модели
  --no-critic         отключить проход-рецензент
  --no-cache          не брать ответы модели из кэша .cache/
```

Поддерживаемые входные форматы: **PDF**, DOCX, Markdown, TXT, HTML.

## Как это работает

```text
документ ─► загрузчик (PDF/DOCX/MD; строки нумеруются)
        ─► 1. детерминированный линтер ──────────────┐ подсказки
        ─► 2. LLM: нарезка на требования + цитаты     │
        ─► 3. LLM: каждое требование × 9 свойств §5.2.5 ◄┤
        ─► 4. LLM: весь набор §5.2.6 / IEEE 830 4.3  ◄┘
        ─► 5. проверка цитат: каждая цитата ищется в исходном тексте (анти-галлюцинации)
        ─► 6. LLM-рецензент: убирает ложные срабатывания и дубли, калибрует серьёзность
        ─► 7. LLM: уточняющие вопросы, итог, приоритеты исправлений
        ─► 8. (опц.) диалог с автором: ответы закрывают дефекты, итог пересчитывается
        ─► отчёт .md + .json
```

Ключевые решения:

* **Привязка каждого дефекта к тексту, проверенная программно.** Модель обязана дать дословную цитату
  и номера строк. Агент сам ищет цитату в документе: точное совпадение, нечёткое, затем совпадение
  по порядку слов (для таблиц PDF, где колонки перемешаны). Замечание без подтверждённой цитаты
  в отчёт не попадает.
* **Гибрид правил и LLM.** Линтер без LLM находит размытые слова, заглушки, незаполненные поля и
  чек-листы, смешение единиц, изменение данных через `GET`, неописанные HTTP-коды, отсутствие
  отката/ИБ/мониторинга, приоритетов. Его находки идут модели как подсказки и проходят того же рецензента.
* **Независимый рецензент** (отдельный проход) повышает точность: в отчёт не попадают придирки и дубли.
* **Уточняющие вопросы** с вариантами ответа и предложением агента, привязанные к дефектам.
  В режиме `-i` агент спрашивает автора и пересчитывает итог.
* **Воспроизводимость:** дисковый кэш ответов модели; в паспорте — SHA-256 документа, модель,
  версия агента (= тег релиза на GitHub).

## Состав отчёта

0. Паспорт прогона: документ, дата, модель, версия агента, токены, время этапов.
1. Нарезка: таблица «ID в отчёте — ID в документе — тип — строки — формулировка — цитата».
2. Проверка каждого требования: матрица по 9 свойствам и замечания с цитатой, строкой, объяснением,
   исправлением и предложенной формулировкой.
3. Проверка набора: свойства §5.2.6 и IEEE 830, противоречия с обеими сторонами, покрытие приёмкой.
4. Сводка: число требований и дефектов, критичные дефекты по группам (непроверяемые, противоречивые, неполные).
5. Уточняющие вопросы к автору.
6. Итог: можно ли начинать разработку и тестирование, что исправить в первую очередь.

## Лимиты бесплатного тарифа

У бесплатного ключа Gemini ограничено число запросов в минуту и **в сутки** (для `gemini-3.6-flash` — около 20).
Один прогон документа кейса тратит примерно 8 запросов. Агент:

* при поминутном лимите (429) сам ждёт 30–90 секунд и повторяет запрос;
* при исчерпании дневного лимита сразу останавливается с понятным сообщением;
* кэширует ответы модели в `.cache/`: повторный прогон того же документа не тратит квоту,
  а прерванный прогон доберёт только недостающее.

Если дневной лимит исчерпан, можно взять другую модель: `--model gemini-3.5-flash-lite`.

## Результаты на документе кейса

Финальный отчёт: [`reports/report.md`](reports/report.md) (данные: `reports/report.json`).

Полнота измерена по экспертному эталону `eval/golden.json` (26 дефектов: 4 критичных, 17 существенных, 5 незначительных):

| Версия | Что менялось | Полнота | Замечаний в отчёте |
| :--- | :--- | :---: | :---: |
| v1.0.0 | первая версия | 92% | 39 |
| v1.1.0 | рецензент не удаляет критичные, сохраняет цитаты при слиянии | 96% | 46 |
| v1.1.1 | правило «откат / ИБ / мониторинг только в шаблоне чек-листа» | 100% | 61–68 |
| v1.3.1 | агрессивное подавление шума | 85% | 29 |
| **v1.3.2** | **баланс: полнота + одно замечание о трассируемости вместо N, игнор артефактов PDF** | **96%** (критичные 4/4, существенные 17/17) | **51** |

Вывод: правила «против шума» в промпте снижают полноту сильнее, чем дубли мешают читателю.
Поэтому шум убирается детерминированно (агрегирование, проверка цитат), а не запретами для модели.

## Оценка качества

`eval/golden.json` содержит экспертный эталон из 26 дефектов документа кейса. Агент этот файл **не читает**.
Он нужен только для измерения полноты:

```bash
python eval/score.py reports/report.json
```

## Структура

```text
validator/
  __main__.py   CLI
  document.py   загрузка PDF/DOCX/MD/HTML, нумерация строк, поиск цитат
  rules.py      детерминированный линтер
  topics.py     правило «откат / ИБ / мониторинг»
  criteria.py   критерии ISO/IEC/IEEE 29148 и IEEE 830
  prompts.py    промпты этапов
  llm.py        клиент Gemini / OpenAI-совместимых / Anthropic / Ollama, JSON, повторы, кэш
  pipeline.py   конвейер агента
  report.py     отчёт Markdown
eval/           эталон и скрипт оценки полноты
samples/        документ кейса (MD)
reports/        отчёты прогонов
```
